# VETTA — BACKEND, DEPLOYMENT AND DISTRIBUTION

Status: **foundation built and tested; not yet serving real users.** Stack decision (owner, 2026-10-25): all-Cloudflare
(Workers + D1). Related: docs/SOCIAL.md (features and privacy model), docs/ROAD_INTELLIGENCE.md (what the road data means).

## 1. Principles
1. **Local-first.** Everything works with no account and no server: recording, scoring, segments, routing, voices.
   An account adds sync and social. A server outage never stops the cockpit.
2. **The server holds the least it can.** Merged per-road numbers, scores the user chose to share, relationships.
   Never a trace, never a raw recording, never audio of anyone's voice.
3. **Phones never talk to the database.** Only the Worker API does; there is no public database key to misconfigure.
   Authorization is code in one place (`backend/src`), covered by tests that fail the build if a privacy rule breaks.
4. **Zero budget, no lock-in.** Free tiers; D1 is SQLite and exports as plain SQL.
5. **Proprietary.** All rights reserved (LICENSE). Third-party notices in THIRD_PARTY_NOTICES.md.

## 2. Vocabulary
- **Bin**: a 5 m stretch of road, identified by (OSM way id, direction, bin index). Holds what the *road* is like (banking,
  roughness, crest). No speed, no time, nothing about the driver.
- **Trace**: the whole recorded path with timestamps and speeds. Reveals home, routine and speed. **Never uploaded.**
- **Pass**: one drive over a segment, scored (Driver Score, optional private time). Stays on the phone unless shared.
- **Segment**: a user-made stretch of road. A friend can *adopt* a shared segment; copies stay linked (`origin_id`) so boards line up.
- **Stage**: a road worth driving (web/stages.js); a route is stages plus connectors. **Highlight**: a user-added scenic point, rated by members.

## 3. Crowdsourced road data with local-first
```
drive → phone profiles it (core/ApexKit, offline) → [opt-in + online] → bin summaries, shuffled, in batches
      → Worker: validate, hold ≤14 days for ranking, nightly merge into per-bin aggregates, award points
      → phone downloads merged values for roads it drives (cached, versioned)
```
- Contributing is opt-in per account (default off). Without it nothing leaves the phone.
- **Real time (owner decision 2026-10-25):** no holding period and no nightly job. A drive streams as chunks (a run of 5 m bins on one road); each chunk is merged into `road_bins` and paid in the same request. A retried chunk is recognised and merged once.
- **Crowd bumps (IDEAS Q-02, 2026-11-11):** each bin's upload may carry `bp` (the phone felt a spike there, 1 / 0 / unknown). `road_bins.bump_hit` / `bump_pass` are sums of 2^((day − 2026-01-01) / 120 d), so dividing by today's weight is a 120-day half-life with no exponent in SQL (D1 refuses `power()`); `bump_drivers` counts different people per spot through a keyed hash per person and 40 m in `seen`. `GET /api/roads` adds `bp: [[bin, posterior]]` per direction for bumps whose Jeffreys Beta posterior over ±2 bins is over 0.8 with 2+ drivers (roads.ts `verifiedBumps`, migration 0052, flag `crowd_bumps` on the phone).
- Client trims a random 0.5–1.5 km at each end of a trip, skips residential/service ways, spreads one trip's upload over days.
- **Small-group caveat:** with under 20 users, "at least k contributors" hides little. `min_contributors` is a setting (friends phase: 1,
  data visible to signed-in members only). Raise to 3 before any public launch.

## 4. Points ("Octane")
- **km of newly mapped road × multiplier, per road segment and direction** (one OSM way, one direction): **1st 3×, 2nd 2×, then 1×.**
- Order is by **arrival**: the first person to upload a road+direction gets 3x, the second 2x, everyone after 1x. A person earns points on their **first drive** on a road only (later drives still improve the data). All chunks of one drive keep the multiplier its first chunk earned. Points land immediately; public: totals only, never who was first. An offline phone that uploads late simply ranks later.
- Anti-cheat (no device attestation exists, so cheap checks): value ranges and contiguity checks, 600 km/day and 1,500 km/week caps, 300 uploads/hour, `driven_on` within 14 days of upload. The cross-account replay check was removed with the holding period (nothing to compare against); with a small group of friends that risk was accepted; open sign-up (2026-10-30) widens it, so look again before a public launch. Privacy: the server keeps no coordinates, no times beyond the day, and `rank_slots`/`road_floor`/`seen` hold only HMAC values keyed by a server secret.

## 5. Data model (backend/migrations, D1 = SQLite)
Applied to both `apexnav-db` and `apexnav-preview-db`: **0001_init.sql**, **0002_segment_sharing.sql**, **0003_camber_count.sql**, **0004_realtime_ingest.sql**.

**Query budget:** Workers Free allows 50 D1 queries per request, and an `env.DB.batch` counts as one. Read or write per row in a batch (or fold the check into the SQL), never one query per row in a loop. `src/query_budget.ts` counts every request. The tests run with `QUERY_LIMIT` 50, so a route over it fails there as it would in production. In production, a request over 40 is counted in `error_counts` under kind `queries`, page = the route.

## 6. Authorization model (what the tests prove)
Implemented in `backend/src/{auth,social,segments}.ts`, one router in `index.ts`.
- **Gate**: signed in (Google or Apple) and not banned. Since 2026-10-30 (the owner: "Vetta is not invite-only at all";
  REVIEW_PEOPLE P-02) every sign-in makes the person a member (`startSession` → `admit`), and a session from before then is
  admitted on its next request (`viewer`); the ban is checked in the same statement. `requireMember` still guards the shared-data
  routes and still answers 403 `invite_required` for a banned account, the code old builds know; `/api/me` keeps `member`.
  Anonymous sessions read nothing.
- **Friend links** (`POST /api/invites`, `/api/invites/preview` `{token}` → `{from}`, `/api/invites/redeem`): an account invite is
  "add a friend" now: one use, 7 days; redeeming makes the two friends (sharing off), never across a block, and for a member
  who joined in the last day with no inviter yet records the sender as `invited_by` (the referral and report counting). The
  App Review code still answers yes (old builds send it) and makes no friendship.
- **Crew links (P-02, P-07, migration 0042)**: `POST /api/crews/:id/invite` by any member of the crew unless the owner set
  `PUT /api/crews/:id/invites {by: "owner"}` (403 `owner_invites_only`; `{by: "anyone"}` is the default), which voids the other
  members' live links. A link works only while its maker is still in the crew. `POST /api/crews/join {token}` joins anyone signed
  in and, on a first join, friends them with the link's maker (not across a block); it answers `{id, friend}` (the sender's
  handle when they are friends). The crew page and `GET /api/crews` carry `invites`; the page also `can_invite`.
- **The crew Score board as totals (the owner's TestFlight note 06, migration 0043, src/drive_scores.ts)**: the app sends each
  drive's Vetta Score and day, `POST /api/drives/scores {drives: [{id, score, driven_on}]}` (50 at most), which keeps a row per
  drive for every crew the driver shares Scores with and is in, and answers `{published, crews}`. `GET
  /api/crews/:id/board?period=week|month|year|all` (members only) answers `{period, rows}`: every member you can see with
  `photo_id`, the `total` of those drive Scores (null when none) and how many `drives`. The grant switched off, leaving or
  the crew ending deletes them; export has `drive_scores_shared`. The page's own `board` (best stage Score this month) stays
  for old builds.
- **Private themes (migration 0044, src/themes.ts, src/private_themes.json)**: `theme_grants (user_id, theme)` rows are written
  by hand only. `GET /api/me` answers `themes`: the full look of each theme granted to the signed-in account ([] for everyone
  else; signed out gets only `{signed_in: false}`); a row naming a theme the server doesn't know is skipped. The app checks
  each look against the theme contract before showing it and drops it when `themes` stops listing it (web/themes.js
  `grant()`). Export has `themes_granted`; the rows go with the account.
- **State-changing requests** must carry our own `Origin` and an `X-ApexNav: 1` header (CSRF), on top of `SameSite=Lax`, `HttpOnly`, `__Host-` cookies.
- **Sharing is per friend and per crew** (on by default for a new friendship and a private crew, `share_defaults.ts`; a public crew asks): a score reaches an audience only through `POST /api/board` and only if a grant for that
  audience exists. `GET /api/board/:canon` returns only entries published **to the viewer**, by someone who is still their friend / crew-mate, whose grant is
  still on, and not blocked either way. Times appear only with `share_times`. `GET /api/board/activity` (IDEAS S-03): the same visibility, the last
  14 days of others' best per day on stages the viewer has, with the viewer's rank on each; scores only, never times.
- **Duels (IDEAS S-24, migrations 0047, 0048):** `POST /api/duels {handle, segment_id, days: 3|7|14, kind?: score|time}` (an accepted friend, your own
  segment; 404 `no_friend` for strangers and unknown handles alike; 409 `duel_exists`; 10 open, 10 a day), `POST
  /api/duels/:id/accept` (opponent only; copies the stage), `DELETE /api/duels/:id` (decline or withdraw), `GET /api/duels`
  (each side's best `driver_score` on the stage inside the window, only from entries published to the other under a live
  `share_scores` grant, plus `time_s` (their quickest) only under `share_times`; friends only, never across a block). Swept 60 days after it ends.
- Unfriend, block, leave crew, revoke grant: the grants and published entries between those people are deleted in the same transaction.
- Friend requests answer identically for unknown, non-member and real handles (no handle enumeration). The requester cannot accept their own request.
- **Keep a convoy going:** `POST /api/convoy/:id/keep` (leader only, in the room's last 30 min, one hour at a time, never past 6 h from its start; 409 `too_early` / `convoy_at_limit`) → `{ expiresAtMs, maxExpiresAtMs }`; every open socket gets `extended` (docs/CONVOY_TRANSPORT.md, `backend/test/convoy.test.ts`).
- **Convoy join codes (IDEAS S-22):** `POST /api/convoy/:id/code` (leader only) → `{code, expiresAtMs}`: six characters of `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (no 0/O, 1/I/L), alive 15 min (never past the convoy); a new one ends the old, the link is not rotated. The room keeps only its hash (`room.code`, like the link's); a `ConvoyIndex` instance named `code:<CODE>` holds which convoy it opens. `POST /api/convoy/code/join {code, consent:true}` and `POST /api/convoy/code/preview {code}` take it loosely (case, spaces, dashes) with the same checks as a link (an older code can't bring back someone who left); every person gets 10 tries in 10 min, right or wrong (429 `too_many_tries`), and every miss is the same 400 `invalid_invite`, so a guess learns nothing (`backend/test/convoy_codes.test.ts`).
- **In-app convoy invites (IDEAS S-22):** `POST /api/convoy/:id/invite-people {handles}` (leader only, up to 15) invites accepted friends and private crew-mates; anyone else, and either side of a block, is skipped silently. The room keeps `invited[userId] = {at, until}` (30 min, never past the convoy), the invitee's `ConvoyIndex` keeps `{name, from, expiresAtMs}` (newest 10). `GET /api/convoy/invites` lists them, `POST /api/convoy/:id/accept {consent:true}` joins with the same checks as a link (an invite older than a leave can't bring someone back; it is used up by the join), `DELETE /api/convoy/invites/:id` dismisses. The leader's link is not rotated. The page polls once a minute while open and toasts a new one (`backend/test/convoy_invites.test.ts`).
- **Shared routes (IDEAS S-05, migration 0012):** `POST /api/routes {name, geom: [[lon,lat]…] ≤ 1,500, friends: handles, crews: ids}` (members; 20 a day; newest 50 kept; only accepted friends with no block and crews you are in, others skipped), `GET /api/routes/shared` (routes shared with you, no shape), `GET /api/routes/:id` (the shape, while the friendship or crew membership holds and no block), `DELETE /api/routes/:id` (owner). Expire after 30 days (daily sweep). The app sends the planned shape without its first 400 m (`backend/test/routes_shared.test.ts`).
- **Crew drive results (IDEAS S-25):** `GET /api/events/:id/record` also returns `results: {stages: [{id, name, rows:
  [{handle, score, place, time_s, gap_s}]}], overall: [{handle, stages, score, full, place, time_s, gap_s}]}` (`resultsSheet`):
  the same Scores as `best` (shared with the crew, the drive's day, those who came), one best per driver per stage; `time_s`
  only while the driver's crew grant has `share_times` (else null); at most 12 stages.
- **Crew drives (IDEAS S-06, migration 0013, `backend/src/events.ts`):** `POST /api/crews/:id/events {title, starts_at (ISO with zone, 10 min to 30 days out), meet {lat, lon, name?}, route_id?, notes?}` (members of that crew; at most 10 upcoming per crew; `route_id` must be a route the planner shared with that crew, S-05; the planner is going), `GET /api/crews/:id/events` and `GET /api/events` (all your crews; from 6 h after the start; who's going by handle, blocked people left out), `POST /api/events/:id/rsvp {status: going|maybe|no}`, `DELETE /api/events/:id` (planner or crew owner; cancels). Car meets (S-13, migration 0015): a public crew's drive created with `public: true` is listed by `GET /api/events/near?lat&lon` to any member within 80 km (crew, time, meeting point, how many going; no handles; whether you're in the crew), while the crew stays public, the drive isn't hidden by reports and neither side blocked the other. Reportable as kind `event` (hidden at the usual report threshold; the owner's remove cancels it). Exported; deleted with the account or crew; the sweep deletes drives a week after they start.
- **Share your ETA (IDEAS S-19, migration 0016, `backend/src/eta_share.ts`; page `web/eta.html`):** `POST /api/eta {left_s}` (members; at most 3 live) returns a random token (only its sha256 is stored); `PUT /api/eta/:token {left_s}` refreshes the arrival time or `{ended: arrived|stopped}` ends it (the owner only); `GET /api/eta/:token` (anyone with the link, signed out) gives the handle, arrival time, last update and whether it ended. No position, route or destination exists in it. Links end after 4 hours; the sweep deletes them a day later.
- **Hazard reports (IDEAS Q-15/Q-16, migration 0011):** `POST /api/hazards {kind, lat, lon, heading?, age_s?}` (members; 30 a day; `age_s` is how long ago a report made with no signal was seen, so it expires from then, and 410 once past its life (F-05); the same kind within 50 m of a live one confirms it instead), `GET /api/hazards?lat&lon&km` (members; live ones within `km` ≤ 50, nearest first, never the reporter), `POST /api/hazards/:id/vote {still}` (one counted vote per person; every still, a person's second included and the reporter's own repeat report, pushes the expiry out by the kind's life: pothole 7 d, gravel 1 d, closure 12 h, debris 3 h, police 1 h, animal 30 min; two or more "gone" outvoting confirmations end it; since 2026-11-12 a "gone" counts only from a member invited or of a week's standing, so fresh accounts can't wipe a warning). Account deletion keeps a report but not who made it; the export lists your own. The daily sweep deletes reports a day after they expire (`backend/test/hazards.test.ts`).
- **Invite previews** (`POST /api/crews/invite/preview` `{token}`, `POST /api/convoy/preview` `{invite}`): members only, the same checks as a join in the same order, and nothing changes. A crew preview gives name, visibility, member count, the owner's handle and `from` (whoever made the link); a convoy preview gives name, the leader's handle (never a real name), size and end time, never the other members. A crew invite (preview and join) answers like an unknown token across a block with the owner, either way, and for a crew that was reported or removed, so nobody learns they were blocked; a full convoy answers 409 before the block check, like a join (`backend/test/previews.test.ts`). Links never join on their own: the page asks with these.
- **Real names** (the Google display name) reach only the person and their accepted friends. Crew member lists, boards and a request you sent (before it is accepted) show the handle only: anyone can join a public crew, and anyone who knows a handle can send a request (`backend/test/names.test.ts`).
- **Rate limits** (`backend/src/ratelimit.ts`, Cloudflare rate limiting bindings in wrangler.jsonc, free): every write 60/min per session (per IP signed out), sign-in start and app code exchange 20/min per IP (not the Google callback or logout); over the limit is `429 rate_limited` with `retry-after: 60` (road uploads already retry on 429). Reads are not limited. Per-feature caps (uploads/hour, km/day, crews, highlights/day) stay on top.
- **Road data shown (owner decision 2026-10-28, `backend/src/roads.ts`, migration 0029):** `GET /api/roads` and `GET /api/coverage` show a road+direction from its first pass when the way is an open road (`road_ways.cls` motorway to tertiary, or unclassified with at least 1.5 km of map line); every other road, an unknown class included, only once two different people have driven it that way (`MIN_DRIVERS`, Z-08), counted in `road_floor` (migration 0058) from established members only: invited, or a member a week. A fresh account still takes its first-driver slot and points in `rank_slots`, but can't be the second driver that makes a lone driver's road visible. Coverage sends `conf` per direction (1 one pass, 2 two to four, 3 five or more), never a count. Per direction it also sends what was measured for stage discovery (web/measured_stages.js, IDEAS R-04): mean `rough`, the `banked` and `offCamber` shares, `crested` (the share of bins two or more passes measured that go light by `CREST_G` 0.15 g or more; null when none did) and `bumps`, how many crowd-verified bumps (`verifiedBumps`, the /api/roads rule) the road has. The phone sends `cls` (its map match's road class) with each contribution; an unlisted value is stored as unknown. Owner-only `GET /api/ops/roads.geojson?bbox=` (≤2° a side, 404 for anyone else) exports an area as GeoJSON for a pilot (docs/ROAD_DATA.md) (`backend/test/roads.test.ts`, `coverage.test.ts`, `loop.test.ts`).
- **App health counts (IDEAS Y-03, migration 0014, `backend/src/health.ts`; client `web/health.js`):** `POST /api/app-health {day, app: ios|web, counts: {metric: n}}`, anonymous (no session read), a finished day up to 7 days old, only the listed metrics (`drives`, `route_ok`, `route_fail`, `route_fallback`, `road_upload_ok`, `road_upload_fail`, `hazard_queued`, `hazard_sent_late`, `calib_locked`, `calib_lock_s`, `directions_said`, `crash_asked`), each 0–100,000. Added into `health_counts` (day, app, metric, n, reports); kept 90 days by the sweep. Owner view `GET /api/ops/app-health?days=7` (404 for anyone else), shown as rates in Crew under the error counts. Phones send only with Settings → Your data → Share app health on (default on).
- **Service check** (owner only, `backend/src/service_check.ts`; client `web/service_check.js`, Settings → Account, 2026-11-12): the owner's phone asks every service the app uses (our API through the app's connection and straight from the page, flags, hazards, coverage, context keys, the OSM relay, the road graph index and a tile, the shipped graph, our router's Fun, Long way and loop plans, Valhalla, OSRM, each Overpass camera server and the app's own camera path, OpenFreeMap style and tiles, terrain, Photon, Nominatim, Open-Meteo, NWS) at a fixed test place in downtown Cincinnati, then `POST /api/ops/service-check {app, version, build, online, results: [{id, state: up|slow|down|skip, http, ms, detail}]}`. No migration: each result adds one to today's `error_counts` row with kind `service` and message `<id>: <state>`, its `stack` the latest run's JSON (http, ms, detail, at, version, build). Read: `SELECT day, source, message, n, stack, last_at FROM error_counts WHERE kind = 'service' ORDER BY last_at DESC`, or `GET /api/ops/service-check?days=3`. `GET /api/ops/service-check/server`: which bindings and secrets are set (booleans only), D1, and the graph-data branch and Overpass mirrors asked from Cloudflare. All three 404 for anyone but the owner. Runs by itself once a launch at most every 6 h, and on Run check. The daily sweep cron (06:23 UTC) also keeps the Worker's own side with no phone: source `server`, ids `srv_db`, `srv_config`, `srv_graph_data` and `srv_overpass_*` (the phone's Overpass ids with `srv_` in front). A probe the app was hidden through is sent as `skip` ("the app was in the background") and asked again once the app is back.
- **Map data in R2** (`backend/src/data_store.ts`, big bet #1, 2026-11-13): the road graph's tiles, the context grid's bundles and the camera list live in our R2 bucket `apexnav-data` (binding `DATA`; previews read the same bucket). `/api/graph/v1/*`, `/api/ctx/v1/*` and `/api/cameras/v1/region.json` read R2 first and fall back to raw.githubusercontent.com (the graph-data branch), so nothing breaks before a mirror run or during an R2 hiccup; a tile served from R2 says `x-cache: r2`. CI fills it: `.github/workflows/data-mirror.yml` runs after each graph, context-grid or camera build (and on demand) and `tools/graph_etl/upload_r2.sh` sends each file to `PUT /api/ops/data?key=…` with the run's GitHub OIDC token (audience `vetta-data`), which `src/github_oidc.ts` checks against GitHub's keys: only this repository's main branch gets in (by repository and owner id, not only the name), and only from the two upload workflows (`workflow_ref`: data-mirror.yml, graph-us.yml) on a push, schedule, dispatch or workflow_run, never pull_request_target, and no secret is stored anywhere. Keys are an allowlist; a graph build's tiles go under `graph/v1/b/<build>/` and its index is refused (409) until every tile it lists is there, so the switch is atomic; builds other than the live one and the one before are deleted. Same bytes again (sha-256 in the object's metadata): no write.
- **Official traffic events** (`backend/src/traffic.ts`, 2026-11-14): `GET /api/traffic/v1/events.json`, public, no position asked: INDOT CARS events and KYTC WZDx (keyless) and, with the secret `OHGO_API_KEY` (or `ohgoApiKey` in `CTX_KEYS`), OHGO incidents, construction, travel delays and dangerous slowdowns, compacted to `{ id, kind, label, lat, lon, road, until, src, heading? }` rows (kinds: closure, closed_way, lane, roadwork, slow, crash, traffic) and kept 5 min in the edge cache; 502 when no feed answers. The phone (web/road_events.js) shows what is near and routes round full closures.
- **Usage guard** (`backend/src/usage.ts`, the owner 2026-11-13: Workers Paid at $5 and not a cent more). Cloudflare's Spend Management block (Billing → Spend Management) stops Workers requests and CPU and Durable Objects past the plan, but not D1, KV or R2. So the Worker meters those itself: every D1 result's `meta.rows_read` / `rows_written` (in the counted DB, `src/query_budget.ts`; `first()` runs as `all()` to get its meta) and every KV get / put / delete / list on the `BACKUPS`, `PHOTOS`, `OSM` and `CTX` bindings, summed per isolate and flushed every 30 s into `error_counts` (no migration: source `server`, kind `usage`, message `d1_read` | `d1_written` | `kv_read` | `kv_write`). Once this calendar month's sum of any of them reaches 80% of the plan's included amount (25 B rows read, 50 M written, 10 M KV reads, 1 M KV writes), `POST /api/contribute` and `POST /api/photos` answer `503 {error: "service_unavailable", scope: "uploads", until: <the 1st, ISO>}` and the weekly backup is skipped; everything else works. The app says it once (web/sync.js `apex:server-down`, scope `uploads`). Read: the Service check's server side (`usage`: used, share, shedding, until), or `SELECT message, SUM(n) FROM error_counts WHERE kind = 'usage' AND day >= strftime('%Y-%m-01', 'now') GROUP BY message`. It is a floor: an evicted isolate loses its last seconds. Kind `usage` is left out of the error views and the failing-route check.
- **Crash reports** (`POST /api/errors`, `backend/src/errors.ts`; client `web/errors.js`, loaded first on every page): uncaught errors and unhandled rejections, and (kind `route`, since 2026-11-11) a Fun / Long way / loop plan our router couldn't make as its reason code only (`fun: index`, `loop: out`, `max: failed (worker message)`; never a place or trip), at most 5 per page load, anonymous (no cookie, no bearer; the app origin may post it signed out). Message, stack and page path are scrubbed on the phone and again in the Worker (URL queries, e-mails, precise numbers, token-like strings). Each one writes a `client_error` log line (Cloudflare → Workers → apexnav → Logs) and adds one to today's row in `error_counts` (migration 0010: day, source ios/web/server, kind, scrubbed message, page, count, first stack; no user, session or IP; 500 distinct rows a day, then one overflow row; kept 30 days). The Worker's own 500s are counted there too, under the route pattern (`GET /api/crews/:id/members`, never the concrete path). The owner reads the last 1-30 days, most frequent first, at `GET /api/ops/errors?days=7` (404 for anyone else); with D1 access alone: `SELECT * FROM error_counts ORDER BY day DESC, n DESC`.
- **Garage** (`garage.ts`, migration 0008): a car card is shown only when its owner switches `shared` on, and then only to accepted friends and
  members of the same **private** crew (anyone can join a public crew, so it doesn't count), never across a block either way, never for an owner with no
  handle. No owner id, location or drive data is in it. Ten cars at most (checked inside the insert); always exactly one primary while you have any.
- **Block and report** (`safety.ts`, `reports_sql.ts`, migration 0009): block by id or handle (unknown handles answer like real ones), list and
  unblock your own blocks (never who blocked you; unblocking restores nothing). `POST /api/reports` covers people, crews, cars and highlights, only
  ones the reporter could see (else 404), one per person per target, 20 a day (checked before any lookup, so no handle oracle). Open reports from
  three current members **invited by different people and not by one another** (one member's spare accounts count once; since sign-up opened, a
  member nobody invited counts only once their membership is a week old) take a public crew off discovery and public join, a car out of
  friends' garages, a highlight off the map, until the owner (OWNER_EMAIL) decides in `GET /api/moderation` (shows reporters and who invited them).
  Dismiss closes those reports for good (the same people can't re-trigger it). Remove keeps it down (`status='removed'`; the owner of a crew or car
  can't make it public/shown again); for a person it is a ban: membership, sessions, app sign-in codes and unused invites go, their crews turn
  private and cars unshown, live convoys drop them, and no invite (nor their own) lets them back, even after deleting and re-creating the account (bans are keyed on the Google account). Export and account deletion need only sign-in.
- **Weekly time attack** (`time_attack.ts`, migrations 0049, 0051, 0054; docs/SOCIAL.md 2.9): `ta_weeks` (the week's loop per cell: its id `ta-…`, name, length, geom `[[lat, lon]…]`, `tries` and `removed` for a moderator's take-down), `ta_joins` (who entered the week), `ta_entries` (your quickest time that week per cell, with that run's Score); `ta_pool` (members' stages put up) is no longer read. `GET /api/timeattack?lat&lon` (the cell only; the phone sends its middle; no loop yet: `make {seed, km}`), `POST /api/timeattack/circuit {cell, seed, name, geom}` (the loop a phone built from this week's seed: closed within 250 m, starts in the cell, 5-25 km measured on the server, no 2 km jumps, and on through roads in Vetta's graph tiles, sampled every 200 m, at most 60 points (`loop_check.ts`: 400 `not_on_roads`; a tile that can't be had leaves it unchecked); the first kept, a race answers with it; a stale seed is 409), `GET /api/timeattack/circuits` (the weeks you entered), `POST /api/timeattack/enter {cell}` (a linked copy in your Stages, and the opt-in), `POST /api/timeattack/runs {runs:[{segment_id, time_s, driver_score, driven_on}]}` (≤20; only this week's loop you entered, driven this week; over 60 m/s average is refused), `DELETE /api/timeattack/entry?lat&lon`. A handle is needed to enter or post times. Blocks hide both ways; report kind `circuit` (removing marks the week's loop removed, deletes its times and entries, and the next phone builds another from the next seed). Swept after eight weeks; in the export (`backend/test/time_attack.test.ts`).
- **Fixed time attacks** (`ta_fixed.ts`, migration 0057; the owner, 2026-11-12: static best roads, a featured one in turn, boards by week, month, year and all time): `ta_circuits` (up to three loops per cell a season, a calendar quarter: id `ta-…`, slot 0-2, name, length, geom, `tries`/`removed`), `ta_entered` (the opt-in), `ta_times` (your quickest time each day you drove one, with that run's Score). `GET /api/ta?lat&lon[&id][&period=week|month|year|all]` (the season's circuits, the featured one marked, one a week in slot order; `make {slot, seed, km, best, avoid}` while a slot is empty; the board of `id` or the featured one for the period), `POST /api/ta/circuit {cell, slot, seed, name, geom}` (checked as the weekly loop, and starting 3 km or more from the area's other loops), `GET /api/ta/entered`, `POST /api/ta/enter {id}`, `POST /api/ta/runs` (as the weekly one: entered, this season, not before you entered), `DELETE /api/ta/entry?id` (all your times on it go). Blocks hide both ways; report kind `circuit` takes one down with its times and its slot is built again from the next seed. Seasons kept two years; in the export (`backend/test/ta_fixed.test.ts`). The weekly endpoints stay for older builds.
- Invites and sessions are stored as SHA-256 hashes; an invite works once, expires after 7 days, and is redeemed atomically.
- Verified by `backend/test/*.test.ts` (76 tests; each privacy rule was checked by temporarily reintroducing the bug and seeing the test fail).

## 7. Auth: Google sign-in, no library
`/api/auth/google/start` → Google (authorization-code flow, PKCE S256, `state`, `nonce`) → `/api/auth/google/callback`: exchanges the code
server-side, checks `iss`, `aud`, `exp`, `nonce`, `email_verified`, creates a 30-day session and makes the person a member unless they are banned (open since 2026-10-30; before then the first
`OWNER_EMAIL` sign-in was the first member and everyone else needed an invite). **Secrets** (set in the Cloudflare dashboard, never in the repo): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`,
`OWNER_EMAIL`, `PEPPER`. Without them the sign-in routes answer 503 and the rest of the app is unaffected.
Google setup (owner, free): Google Cloud console → OAuth consent screen (External, publish "In production"; basic scopes only) → OAuth client (web) with redirect
`https://<site>/api/auth/google/callback`. The native sideloaded app must use the system browser for sign-in (Google blocks embedded web views).

## 9. Highlights
User-added scenic points, rated by members, that can pull a route toward them (toggle + strength slider in the route panel).
- Lookup is a **bounding-box query** (`lat`/`lon` indexes) around the route, filtered by distance on the phone; no spatial extension needed at this scale.
  If it outgrows that, highlights is a small table to move to a PostGIS database.
- Built (`backend/src/highlights.ts`): members only; author never returned; 10 new per day and 200 per person; duplicates within 40 m refused; US coordinates only;
  score = (sum of stars + 6) / (ratings + 2) so one account cannot pin a spot at 5.0; the author cannot rate their own; three different reporters hide a spot.
- Author is never shown. Members only, rate-limited, report button. "Visited" on a rating is proved by the rater's own drive passing within ~150 m
  (decided on the phone; the server never sees the trace). Highlights at a user's own start points are never offered (home privacy).
- Routing: the loop planner (web/stages.js) adds a bonus to stages near a highlight, scaled by rating and capped by a detour limit.

## iOS app access (ios-api, 2026-10-26)
The app serves `web/` from `apexnav://app`, so `/api` is cross-origin to the Worker. `web/sync.js` `ApexSync.apiFetch` sends
`https://apexnav.senftns.workers.dev` + path with `Authorization: Bearer <session token>` in the app and the same-origin cookie on the web.
The Worker answers CORS only for `Origin: apexnav://app` (no credentials); writes from that origin need the bearer token (no cookie CSRF path).
Sign-in: Google refuses embedded web views, so the shell opens `ASWebAuthenticationSession` on `/api/auth/google/start?app_challenge=<S256 of verifier>`;
the callback redirects to `apexnav://auth?code=…` (single use, 2 min, stored hashed in `app_auth_codes`) and the shell trades
`{code, verifier}` at `POST /api/auth/app/exchange` for a session token, handed to the page (`onNative({type:'session'})`, kept in localStorage).

**Sign in with Apple (app only, IDEAS O-05):** the shell runs `ASAuthorizationAppleIDProvider` with the sha256 hex of a one-time nonce and posts `{id_token, nonce, name}` to `POST /api/auth/apple` (`backend/src/apple.ts`). The Worker verifies the RS256 signature against `https://appleid.apple.com/auth/keys` (cached an hour, refetched for an unknown kid), then `iss`, `aud` = `com.senft.ApexNav`, `exp` and the nonce, and returns a session token like the code exchange. The account is `users.google_sub = 'apple:<sub>'` (the column holds the sign-in identity, so bans apply); Apple's name arrives only on the first authorization and is kept; a hidden email is Apple's relay address. Deleting the account revokes Apple's token (`backend/src/apple_revoke.ts`, #503) once the owner's Sign in with Apple key and secrets are set (docs/OWNER_TODO.md); without them the deletion still goes through.
